# crescent

Менеджер фоновых задач для Codex: следит за сессиями `/goal`, ждёт сброса лимита
и перезапускает их, чтобы длинная работа не умирала на пятичасовом окне.
Поставил задачу — она крутится, пока вы спите.

Нативное окно без CGO — на [goWidgets](https://github.com/unxed/goWidgets).
На Windows собирается как GUI-приложение, без консольного окна.

> **Статус: читающая половина.** Сейчас утилита находит цели на диске и
> показывает их в окне. Она **ничего не запускает и не пишет** в Codex —
> перезапуск сессий делается следующим шагом.

<details>
<summary>Откуда название</summary>

Растущий месяц — неполная луна. Во-первых, работа по ночам. Во-вторых, у Codex
есть модель `gpt-5.6-luna`, и это не номер версии, а постоянный уровень линейки
Sol / Terra / Luna. В-третьих, «неполная» здесь буквально: утилита живёт в
остатке — в той части окна лимита, которую вы не выбрали сами.

## Сначала — `-dump`

Формат rollout-файлов Codex не документирован и уже менялся (время сброса
переехало с относительных смещений на абсолютные метки в openai/codex#5304).
Парсер написан терпимым к схеме, но проверить его можно только на живой машине.
Поэтому первым делом:

```sh
crescent -dump
```

Отчёт покажет, сколько файлов найдено, у скольких распознана цель и у скольких —
время сброса лимита. Если целей ноль, значит парсер не знает имён полей вашей
версии Codex:

```sh
crescent -dump -keys
```

добавит список **имён** JSON-полей с частотами. Только имена: ни одного значения
из ваших сессий в вывод не попадает, поэтому его можно спокойно прикладывать к
issue. По этому списку парсер расширяется за пару строк в `internal/codex/scan.go`.

Каталог по умолчанию — `$CODEX_HOME`, иначе `~/.codex` (на Windows —
`%USERPROFILE%\.codex`). Переопределяется:

```sh
CODEX_HOME=/путь/к/.codex crescent -dump
```

## Окно

```sh
crescent
```

Показывает возобновляемые цели: завершённые и заблокированные отфильтрованы,
потому что первым нечего делать, а вторым нужен человек, а не повтор.
У сессии, упёршейся в лимит, рядом стоит время сброса.

## Сборка

```sh
# Windows — без консольного окна
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -ldflags="-s -w -H windowsgui" ./cmd/crescent
# Linux
CGO_ENABLED=0 GOOS=linux   GOARCH=amd64 go build -ldflags="-s -w"               ./cmd/crescent

go test ./...
```

Бэкенд GUI выбирается автоматически; для проверки без окон:

```sh
goWidgets_BACKEND=headless crescent
```

## Как устроено чтение

`internal/codex` не разбирает rollout по фиксированной структуре. Он обходит
каждую JSON-запись рекурсивно и подбирает знакомые ключи в разных написаниях
(`resets_at` / `resetsAt` / `resetsInSeconds`, `cwd` / `workingDirectory`,
`goal.objective` / `goalStatus` и так далее), где бы они ни лежали. Из файла
читаются только первые и последние 256 КиБ: сверху идентичность, снизу текущее
состояние, а середина в сессии на сотни мегабайт не нужна.

Незнакомый статус цели считается возобновляемым — если Codex заведёт новое
состояние, crescent не перестанет видеть цель молча.

Числовые метки времени распознаются по порядку величины: секунды, миллисекунды,
микросекунды и наносекунды от эпохи.

## Что дальше

1. Перезапуск сессии после сброса лимита: `codex exec resume <id>` под
   наблюдением, разбор потока `--json`, ожидание по стенным часам (чтобы сон
   ноутбука не ломал отсчёт).
2. Не мешать интерактивной работе: если rollout-файлы менялись только что —
   вы за клавиатурой, crescent стоит в стороне. Лимит общий на аккаунт, поэтому
   цели гонятся последовательно, а не параллельно.
3. Трей и сворачивание вместо закрытия. На Windows `Shell_NotifyIcon`; на Linux
   `StatusNotifierItem` по D-Bus, поскольку `GtkStatusIcon` устарел.
4. `ListView` в goWidgets вместо стека чекбоксов, когда целей станет больше десятка.
