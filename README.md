# crescent

Менеджер фоновых задач для Codex: перезапускает цели, как только сбрасываются
лимиты. Поставил задачу — она крутится, пока вы спите.

Нативное окно без CGO — на [goWidgets](https://github.com/unxed/goWidgets).

> **Статус: переписывается на штатный интерфейс Codex.**
>
> Первая версия читала rollout-файлы напрямую и запускала `codex exec resume`
> вторым клиентом. Она работает и сохранена в [`archive/`](archive/) вместе с
> подробным разбором, почему отложена, — но, пока запущено приложение ChatGPT,
> Codex справедливо не даёт второму писателю трогать свои треды.
>
> У Codex есть app-server с JSON-RPC, где всё нужное берётся тремя запросами:
> `account/rateLimits/read` — можно ли работать, `thread/list` — какие есть
> цели, `turn/start` — запустить. Новая версия строится на нём.
>
> Запустить прежнюю: `go run ./archive/cmd/crescent -run`

## Первая проверка

```sh
go build ./cmd/crescent
./crescent -doctor
```

Поднимает `codex app-server` дочерним процессом, здоровается и спрашивает три
вещи: лимиты аккаунта, список тредов, цель каждого. Если показанное совпадает с
тем, что показывает приложение, — фундамент верен, и дальше остаётся петля.

## Перезапуск

```sh
crescent -restart -dry-run   # показать, что было бы перезапущено
crescent -restart            # перезапустить
```

Спрашивает лимиты, и если работать можно — берёт цели, которые Codex сам
пометил как остановленные (`usageLimited`, `paused`), и каждой шлёт ход.
Завершённые и заблокированные не трогает: первым нечего делать, вторым нужен
человек.

Если состояние лимитов выяснить не удалось, не запускается ничего. Неизвестность
— не разрешение.

**Читать можно при запущенном приложении, запускать — нет.** Список тредов и
лимиты приходят в любом случае; а вот ход требует единоличного владения
сессией, поэтому перед запуском приложение должно быть закрыто. `-restart` это
проверяет и откажется, пока оно работает.

## Сначала — `-dump`

Формат rollout-файлов Codex не документирован и уже менялся (время сброса
переехало с относительных смещений на абсолютные метки в openai/codex#5304).
Парсер написан терпимым к схеме, но проверить его можно только на живой машине.
Поэтому первым делом:

```sh
crescent -dump
```

Отчёт покажет лимиты аккаунта, список найденных целей и — для каждой — из какого
именно JSON-поля взята цель и её идентификатор. Если целей ноль, значит парсер не
знает имён полей вашей версии Codex:

```sh
crescent -dump -keys
```

добавит список **имён** JSON-полей с частотами. Только имена: ни одного значения
из ваших сессий в вывод не попадает, поэтому его можно спокойно прикладывать к
issue. По этому списку парсер расширяется за пару строк в `internal/codex/scan.go`.

Каталог по умолчанию — `$CODEX_HOME`, иначе `~/.codex` (на Windows —
`%USERPROFILE%\.codex`). Переопределяется:

```sh
CODEX_HOME=/путь/к/.codex crescent -dump
```

## Проверка окружения и план

```sh
crescent -doctor
```

Отвечает на вопрос «а сработает ли тут вообще»: найден ли `codex`, знает ли эта
сборка `exec resume` и `--json`, существуют ли кэши Go и живы ли рабочие каталоги
целей. Многие сессии запускались из `/tmp`, а он не переживает перезагрузку.

`codex` ищется не только в `PATH`. Отдельного CLI может не быть вовсе: десктопное
приложение ChatGPT несёт Codex внутри себя, и на машине с ежедневной работой в
Codex `whereis codex` возвращает пустоту. Поэтому кроме `PATH` просматриваются
пользовательские каталоги (`~/.local/bin`, префиксы npm и nvm), каталоги с
версией в имени и, последним средством, установка самого приложения обходом с
ограничением глубины — раскладка там не документирована и меняется.

Если бинарник всё-таки не нашёлся, `-doctor` печатает список просмотренных мест.
Путь можно задать явно:

```sh
crescent -codex /путь/к/codex -doctor
export CRESCENT_CODEX=/путь/к/codex     # то же самое через окружение
```

```sh
crescent -plan
```

Печатает решение, ничего не выполняя: какие цели в очереди, в каком порядке и
какой именно командой каждая была бы продолжена. Команду можно скопировать в
терминал и запустить руками.

Два правила, которые видны в плане:

* **Цели идут по одной.** Лимит принадлежит аккаунту, поэтому три цели
  параллельно опустошили бы пятичасовое окно за двадцать минут — а ещё два
  агента могли бы одновременно править один чекаут.
* **crescent уступает человеку.** Если хоть один rollout-файл менялся за
  последние пятнадцать минут, значит вы работаете в Codex сами, и очередь
  целиком встаёт.

## Фоновый режим

```sh
crescent -gui          # окно: цели, состояние, пуск и пауза
crescent -tray         # то же, но сразу свёрнутым в трей
crescent -run          # без окна, в терминале
crescent -status       # что происходит прямо сейчас (из любого терминала)
```

Окно, иконка и демон живут в одном процессе. Разделить их значило бы завести
между ними протокол и позволить иконке пережить работу или окну разойтись с
иконкой в показаниях; один процесс не может разойтись сам с собой.

В окне: строка состояния, счётчики ходов и лимитов, и список целей галочками.
Снятая галочка убирает цель из очереди со следующего хода, не останавливая
остальные. Цели с исчезнувшим рабочим каталогом помечены и сняты сразу.
Закрытие окна прячет его в трей, а если статусной области нет — завершает
работу, потому что спрятать окно без пути назад значит его потерять.

В режиме трея демон живёт внутри того же процесса, что и иконка. Два процесса
потребовали бы протокола между собой и позволили бы иконке пережить работу или
наоборот; один процесс не может разойтись сам с собой. В подсказке иконки —
текущее состояние, в меню — пауза, продолжение и выход.

Консоли в этом режиме нет, поэтому журнал пишется в `crescent.log` в каталоге
кэша пользователя.

Что делает `-run`:

1. **Самопроверка.** Первый ход всегда идёт в read-only песочнице. Вопрос «а
   работает ли resume на этой машине» отвечается программой, а не человеком, и
   отвечается до того, как что-то будет записано в репозиторий. Если codex
   промолчал или выдал не тот формат — демон останавливается и пишет, что
   именно не так и какой командой снять поток. Пропустить: `-no-probe`.
2. **Уступает вам.** Если какая-нибудь сессия менялась за последние 15 минут,
   значит вы работаете в Codex сами, и очередь встаёт целиком. Лимит общий, так
   что ход, взятый сейчас, отнят у вас. Собственные ходы crescent при этом
   исключает: иначе он читал бы свою же запись как вашу работу и делал бы один
   ход в четверть часа.
3. **Ждёт лимит по стенным часам.** Ожидание разбито на короткие интервалы, а не
   один длинный сон: ноутбук, проспавший два часа, должен проснуться со знанием,
   что окно уже открылось.
4. **По кругу, по шагу на цель.** За раз работает одна — три параллельно
   опустошили бы пятичасовое окно за двадцать минут, а два агента подрались бы
   за один чекаут. Но очередь именно вращается: сделав `MaxTurns` ходов подряд
   (по умолчанию один), цель уступает место следующей. Ради этого всё и
   затевалось — чтобы длинная задача не забрала окно целиком, пока остальные
   стоят нетронутыми до конца квоты.

Ctrl-C останавливает между ходами, а не посреди хода.

Состояние публикуется в файл, так что `-status` работает из любого терминала, а
причина аварийной остановки переживает сам процесс.

## Журнал

Оба режима пишут в один файл — `crescent.log` в каталоге кэша пользователя
(путь печатается при запуске и в `-status`). В терминальном режиме вывод идёт
и на экран, и в файл: смотреть за работой вживую и прочитать её потом — не
взаимоисключающие вещи. Файл перекатывается по достижении 4 МиБ, одно
поколение сохраняется рядом как `crescent.log.1`.

## Цель, открытая в приложении

Пока десктопное приложение держит чат открытым, Codex отказывается возобновлять
эту сессию: `thread-store conflict: thread ... already has an active writer`.
Сообщение приходит на stderr, а не в поток событий, поэтому crescent читает и
его тоже — иначе отказ выглядел бы как «codex ничего не напечатал».

Это не ошибка и не повод ждать: цель откладывается на десять минут, и очередь
сразу переходит к следующей. Закроете чат в приложении — цель вернётся в
ротацию сама. Если заняты все цели, crescent так и говорит.

## Один ход под присмотром

```sh
crescent -run-once -read-only
```

Показывает список, сам предлагает подходящую цель — самую свежую из тех, что
действительно можно продолжить, — и ждёт Enter:

```
   1. 01a07e20  active    Проект Лунобот-2. Следуй приложенной инструкции.
✗  2. 01a04f3a  active    Двигайся дальше к полностью portable сборке.

✗ — рабочий каталог не существует, продолжать нечего

Продолжить цель 1 (Проект Лунобот-2. Следуй приложенной ин…)? [Enter — да, номер — другая, q — отмена]:
```

Ничего запоминать и переносить между командами не нужно. Если цель нужна не та,
её можно назвать сразу — номером, началом id или куском текста:

```sh
crescent -run-once -read-only 2
crescent -run-once -read-only 01a07e20
crescent -run-once -read-only лунобот
crescent -run-once -read-only -yes           # без вопросов, для скриптов
```

Печатает, что произошло: поток событий, типы, последнее сообщение, упёрлись ли
в лимит и когда он сбросится.

**Первый запуск делайте с `-read-only`.** Он проверяет всю связку — resume,
авторизацию, разбор потока `--json` — но песочница read-only физически не даст
ничего записать, так что рабочие каталоги в безопасности.

Если формат событий поменялся и ни одна строка не разобралась, сохраните поток
и посмотрите глазами:

```sh
crescent -run-once <id> -read-only -raw /tmp/stream.jsonl
```

## Песочница

Цели продолжаются в `--sandbox workspace-write`: агент правит свой чекаут и
больше ничего. Единственное исключение — кэши Go (`GOMODCACHE`, `GOCACHE`):
они лежат вне рабочего каталога, и без права записи в них сборка либо каждый
раз качает всё заново, либо просто падает. Они добавляются через
`sandbox_workspace_write.writable_roots`.

## Окно

Окно пока только показывает найденное и ничего не запускает, поэтому оно за
флагом, а голая команда `crescent` печатает список и подсказывает следующий шаг. (пока только смотреть)

```sh
crescent
```

Окно — режим по умолчанию, и оно отпускает терминал: запустили и вернулись к
работе. `-foreground` оставляет процесс в консоли, `-no-gui` показывает справку.

Наверху светофор: 🟢 работает, 🟡 ждёт (лимита, сети или закрытия Codex),
🔴 стоит. Под ним — что именно происходит, словами. Дальше цели галочками:
отметил — и она будет перезапускаться после каждого сброса лимита. «Пауза»
останавливает перезапуски, не теряя отметок.

Форки одной цели схлопываются в одну строку: Codex показывает их отдельными
тредами с тем же именем, и вести их все — значит тратить квоту по кругу на одно
и то же.

В окне: список целей галочками, строка состояния сверху и журнал под ним —
видно, что модель делает прямо сейчас. Отметил галочку — сразу видно в
состоянии и в журнале, ждать нечего. Крестик окна прячет в трей, не закрывает:
случайный клик не остановит работу. Полностью выйти — кнопкой «Выйти».

Окно пока умеет только показывать: запустить из него ничего нельзя, поэтому за
флагом. Голая команда `crescent` печатает список целей и подсказывает следующий
шаг. В окне видны возобновляемые цели: завершённые и заблокированные отфильтрованы,
потому что первым нечего делать, а вторым нужен человек, а не повтор.
У сессии, упёршейся в лимит, рядом стоит время сброса.

## Сборка

```sh
# Windows — без консольного окна
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -ldflags="-s -w -H windowsgui" ./cmd/crescent
# Linux
CGO_ENABLED=0 GOOS=linux   GOARCH=amd64 go build -ldflags="-s -w"               ./cmd/crescent

go test ./...
```

Бэкенд GUI выбирается автоматически; для проверки без окон:

```sh
goWidgets_BACKEND=headless crescent
```

## Найти ключ по значению

Формат rollout-ов не документирован, и угадывать имена полей снаружи —
проигрышная стратегия. Но вы видите правильное значение в приложении, так что
вопрос можно развернуть:

```sh
crescent -find "Konsole"           # как называется чат в приложении
crescent -find "Konsole" -deep     # искать во всех файлах целиком, не только
                                   # в той части, которую читает сканер
```

Печатает, под какими ключами лежит это значение и в каком файле. Отдельно
помечает попадания вне области, которую сканер читает, — это ответ на вопрос
«почему сканер этого не видит».

## Лимит принадлежит аккаунту, а не сессии

Снимок лимитов лежит почти в каждом rollout-файле, но в старом файле он
описывает окно, актуальное на момент последнего запуска той сессии. В каталоге
из трёх сотен сессий это означает груду времён сброса, истёкших несколько дней
назад. Поэтому действующим считается снимок из самого свежего файла, а не из той
сессии, на которую вы смотрите.

В одном снимке лежат оба окна — скользящее пятичасовое и недельное. Взять
«последнее попавшееся» значит подбросить монетку, поэтому crescent сохраняет оба
и для планирования берёт ближайшее ещё не наступившее. Если все окна истекли,
лимит сейчас не мешает.

Внутри длинного rollout-а снимок пишется на каждом ходу, поэтому учитывается
только последний: иначе окна, закрывшиеся неделю назад, смешиваются с текущими.

## Что проверяется автоматически

Формат событий `codex exec --json` больше не угадывается: он описан в
`codex-rs/exec/src/exec_events.rs` в открытом репозитории Codex, а формулировки
про лимит — в `codex-rs/protocol/src/error.rs`. Парсер следует им, а мок в
`ci/mockcodex` говорит на той же схеме.

Поэтому CI прогоняет весь цикл без аккаунта: синтетический `~/.codex`, мок
вместо codex, и демон проходит самопроверку, ходы, упирание в лимит и ожидание.
На Windows то же самое — это платформа, которую иначе не проверить руками.

```sh
./ci/rehearsal.sh        # то же самое локально
./ci/rehearsal-wine.sh   # то же, но Windows-сборкой под Wine
pwsh ./ci/rehearsal.ps1  # windows-скрипт: PowerShell есть и под Linux
```

Wine — не Windows, а быстрый первый фильтр: он ловит ошибки, специфичные для
платформы, за секунды и на месте, не дожидаясь раннера. Скрипт прогоняет под
ним и сами модульные тесты, собранные под Windows, — там же, где Windows-job
сообщит о падении минутами позже.

Так уже нашлись: пути к кэшам Go, склеенные через прямой слэш по юниксовой
схеме (`C:\users\me/.cache/go-build` в `writable_roots`); ведущий слэш URL,
попадавший в путь при `file:///C:/...`; и определение исполняемости файла на
Windows, где решает расширение, а не бит доступа.

## Как устроено чтение

`internal/codex` не разбирает rollout по фиксированной структуре. Он обходит
каждую JSON-запись рекурсивно и подбирает знакомые ключи в разных написаниях
(`resets_at` / `resetsAt` / `resetsInSeconds`, `cwd` / `workingDirectory`,
`goal.objective` / `goalStatus` и так далее), где бы они ни лежали.

Файлы читаются целиком. Читать только края было ошибкой: записи цели пишутся
тогда, когда цель ставят или меняют, и в сессии, работающей третьи сутки, текущая
цель оказывается в середине файла — на реальных данных активная цель лежала на
строке 30255 и сканер её не видел вовсе. Именно долгие сессии упираются в лимиты,
так что слепым он был ровно там, где нужен.

Читать целиком получается дёшево за счёт двух вещей. Байтовый префильтр: JSON
разбирается только у строк, содержащих один из маркеров, а в rollout-е, набитом
выводом команд, таких строк доли процента. И кэш по размеру и времени изменения:
неизменившийся файл не перечитывается, так что медленный проход бывает только
первым, а дальше перечитываются лишь растущие сессии. Сбросить: `crescent -refresh`.

Незнакомый статус цели считается возобновляемым — если Codex заведёт новое
состояние, crescent не перестанет видеть цель молча.

Числовые метки времени распознаются по порядку величины: секунды, миллисекунды,
микросекунды и наносекунды от эпохи.

Рабочий каталог Codex записывает то простым путём, то как `file://`-ссылку, и в
последнем случае она percent-закодирована: путь с кириллицей приезжает как
`file:///home/u/%D0%94%D0%BE%D0%BA...`. Такой путь нормализуется, иначе передать
его процессу нельзя.

Имя rollout-файла бывает двух видов: `rollout-<ts>-<uuid>.jsonl` и, для сессии,
продолженной из другой, `rollout-<ts>-<родитель>_<своя>.jsonl`. Идентификатором
считается собственный UUID сессии, родительский показывается отдельно.

Имя файла при этом важнее того, что записано внутри. Идентификатор в теле
rollout-а не обязан принадлежать самому rollout-у: транскрипт ссылается и на
другие сессии — порождённые агенты, продолженные треды. На живом каталоге из-за
этого три файла отчитались чужими идентификаторами, причём два совпали между
собой. Значение изнутри используется, только если в имени UUID нет вовсе.
