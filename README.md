# crescent

Менеджер фоновых задач для Codex: следит за сессиями `/goal`, ждёт сброса лимита
и перезапускает их, чтобы длинная работа не умирала на пятичасовом окне.
Поставил задачу — она крутится, пока вы спите.

Нативное окно без CGO — на [goWidgets](https://github.com/unxed/goWidgets).
На Windows собирается как GUI-приложение, без консольного окна.

> **Статус: читает и планирует, но пока не запускает.** Утилита находит цели,
> показывает их в окне и печатает план — какие сессии, в каком порядке и какой
> именно командой она бы продолжила. Сам запуск делается следующим шагом, так
> что **в Codex она ничего не пишет**.

Растущий месяц — неполная луна. Во-первых, работа по ночам. Во-вторых, у Codex

## Сначала — `-dump`

Формат rollout-файлов Codex не документирован и уже менялся (время сброса
переехало с относительных смещений на абсолютные метки в openai/codex#5304).
Парсер написан терпимым к схеме, но проверить его можно только на живой машине.
Поэтому первым делом:

```sh
crescent -dump
```

Отчёт покажет лимиты аккаунта, список найденных целей и — для каждой — из какого
именно JSON-поля взята цель и её идентификатор. Если целей ноль, значит парсер не
знает имён полей вашей версии Codex:

```sh
crescent -dump -keys
```

добавит список **имён** JSON-полей с частотами. Только имена: ни одного значения
из ваших сессий в вывод не попадает, поэтому его можно спокойно прикладывать к
issue. По этому списку парсер расширяется за пару строк в `internal/codex/scan.go`.

Каталог по умолчанию — `$CODEX_HOME`, иначе `~/.codex` (на Windows —
`%USERPROFILE%\.codex`). Переопределяется:

```sh
CODEX_HOME=/путь/к/.codex crescent -dump
```

## Проверка окружения и план

```sh
crescent -doctor
```

Отвечает на вопрос «а сработает ли тут вообще»: найден ли `codex`, знает ли эта
сборка `exec resume` и `--json`, существуют ли кэши Go и живы ли рабочие каталоги
целей. Многие сессии запускались из `/tmp`, а он не переживает перезагрузку.

`codex` ищется не только в `PATH`. Отдельного CLI может не быть вовсе: десктопное
приложение ChatGPT несёт Codex внутри себя, и на машине с ежедневной работой в
Codex `whereis codex` возвращает пустоту. Поэтому кроме `PATH` просматриваются
пользовательские каталоги (`~/.local/bin`, префиксы npm и nvm), каталоги с
версией в имени и, последним средством, установка самого приложения обходом с
ограничением глубины — раскладка там не документирована и меняется.

Если бинарник всё-таки не нашёлся, `-doctor` печатает список просмотренных мест.
Путь можно задать явно:

```sh
crescent -codex /путь/к/codex -doctor
export CRESCENT_CODEX=/путь/к/codex     # то же самое через окружение
```

```sh
crescent -plan
```

Печатает решение, ничего не выполняя: какие цели в очереди, в каком порядке и
какой именно командой каждая была бы продолжена. Команду можно скопировать в
терминал и запустить руками.

Два правила, которые видны в плане:

* **Цели идут по одной.** Лимит принадлежит аккаунту, поэтому три цели
  параллельно опустошили бы пятичасовое окно за двадцать минут — а ещё два
  агента могли бы одновременно править один чекаут.
* **crescent уступает человеку.** Если хоть один rollout-файл менялся за
  последние пятнадцать минут, значит вы работаете в Codex сами, и очередь
  целиком встаёт.

## Песочница

Цели продолжаются в `--sandbox workspace-write`: агент правит свой чекаут и
больше ничего. Единственное исключение — кэши Go (`GOMODCACHE`, `GOCACHE`):
они лежат вне рабочего каталога, и без права записи в них сборка либо каждый
раз качает всё заново, либо просто падает. Они добавляются через
`sandbox_workspace_write.writable_roots`.

## Окно

```sh
crescent
```

Показывает возобновляемые цели: завершённые и заблокированные отфильтрованы,
потому что первым нечего делать, а вторым нужен человек, а не повтор.
У сессии, упёршейся в лимит, рядом стоит время сброса.

## Сборка

```sh
# Windows — без консольного окна
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -ldflags="-s -w -H windowsgui" ./cmd/crescent
# Linux
CGO_ENABLED=0 GOOS=linux   GOARCH=amd64 go build -ldflags="-s -w"               ./cmd/crescent

go test ./...
```

Бэкенд GUI выбирается автоматически; для проверки без окон:

```sh
goWidgets_BACKEND=headless crescent
```

## Лимит принадлежит аккаунту, а не сессии

Снимок лимитов лежит почти в каждом rollout-файле, но в старом файле он
описывает окно, актуальное на момент последнего запуска той сессии. В каталоге
из трёх сотен сессий это означает груду времён сброса, истёкших несколько дней
назад. Поэтому действующим считается снимок из самого свежего файла, а не из той
сессии, на которую вы смотрите.

В одном снимке лежат оба окна — скользящее пятичасовое и недельное. Взять
«последнее попавшееся» значит подбросить монетку, поэтому crescent сохраняет оба
и для планирования берёт ближайшее ещё не наступившее. Если все окна истекли,
лимит сейчас не мешает.

Внутри длинного rollout-а снимок пишется на каждом ходу, поэтому учитывается
только последний: иначе окна, закрывшиеся неделю назад, смешиваются с текущими.

## Как устроено чтение

`internal/codex` не разбирает rollout по фиксированной структуре. Он обходит
каждую JSON-запись рекурсивно и подбирает знакомые ключи в разных написаниях
(`resets_at` / `resetsAt` / `resetsInSeconds`, `cwd` / `workingDirectory`,
`goal.objective` / `goalStatus` и так далее), где бы они ни лежали. Из файла
читаются только первые и последние 256 КиБ: сверху идентичность, снизу текущее
состояние, а середина в сессии на сотни мегабайт не нужна.

Незнакомый статус цели считается возобновляемым — если Codex заведёт новое
состояние, crescent не перестанет видеть цель молча.

Числовые метки времени распознаются по порядку величины: секунды, миллисекунды,
микросекунды и наносекунды от эпохи.

Рабочий каталог Codex записывает то простым путём, то как `file://`-ссылку, и в
последнем случае она percent-закодирована: путь с кириллицей приезжает как
`file:///home/u/%D0%94%D0%BE%D0%BA...`. Такой путь нормализуется, иначе передать
его процессу нельзя.

Имя rollout-файла бывает двух видов: `rollout-<ts>-<uuid>.jsonl` и, для сессии,
продолженной из другой, `rollout-<ts>-<родитель>_<своя>.jsonl`. Идентификатором
считается собственный UUID сессии, родительский показывается отдельно.

Имя файла при этом важнее того, что записано внутри. Идентификатор в теле
rollout-а не обязан принадлежать самому rollout-у: транскрипт ссылается и на
другие сессии — порождённые агенты, продолженные треды. На живом каталоге из-за
этого три файла отчитались чужими идентификаторами, причём два совпали между
собой. Значение изнутри используется, только если в имени UUID нет вовсе.

## Что дальше

1. Собственно запуск: выполнить запланированную команду, читать поток `--json`,
   ждать по стенным часам (чтобы сон ноутбука не ломал отсчёт) и перезапускать
   после сброса лимита.
2. Трей и сворачивание вместо закрытия. На Windows `Shell_NotifyIcon`; на Linux
   `StatusNotifierItem` по D-Bus, поскольку `GtkStatusIcon` устарел.
3. `ListView` в goWidgets вместо стека чекбоксов, когда целей станет больше десятка.

Известное ограничение: в rollout-ах встречаются только статусы `active` и
`paused`, ни одного `usageLimited`, хотя сессии в лимит упирались. Значит
«цель встала из-за лимита» по статусу не определить — придётся судить по окнам
и времени изменения файла.
